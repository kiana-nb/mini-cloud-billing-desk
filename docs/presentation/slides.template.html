Parts of the system

One command starts db, infra and api; the api also serves the built panel. Workers run in the api process and use leases, so several api instances can run.

Data model: rules the database enforces

  • R13/R14 unique (server or IP, hour): a charge exists once
  • R8 EXCLUDE (ip_id =, during &&): one holder per IP at any moment
  • R7 FK (server, customer): the payer of an IP is the owner of its server
  • R9 trigger: IPs only attach to alive servers (locks the server row)
  • R10 ledger is append-only (update / delete / truncate raise)
  • R11 a charge is one resource and one whole UTC hour
  • R12/R4 idempotency keys for top-ups and server creation
  • R15/R16 a charge is refunded once, by its exact amount
  • R3 an infrastructure server is tracked by at most one record
  • R1 the application clock only moves forward

Money is bigint credits; all times are timestamptz in UTC.

Life cycle of a server

Billing follows server_usage periods, which open at "running" and close at the termination request, not at the infrastructure's confirmation.

Life cycle of an IP address

An IP is billed for the time it is attached to a server that runs: the intersection of the assignment period and the usage period.

What is not safe yet, and what I would do next

  • Billing cost grows with history. Each run recomputes from all usage periods. Next: a per-resource "billed through" watermark and partitioned ledger.
  • Negative balances are allowed. Charges are postpaid; nothing notifies or suspends yet. Next: the dunning flow with a recorded notice as a precondition (FK) for suspension.
  • A server lost by the infrastructure is billed until the reconciler confirms it is gone (every 20 s in the Compose setup). Next: use the infrastructure's own stop time if it offers one.
  • Billing stops at the termination request, even if the delete takes longer. A deliberate customer-friendly choice; we absorb the cost.
  • No monitoring. Failed billing items and drift are stored and shown, but nothing alerts. Next: metrics and an alert on billing_failures.
  • Auth is minimal. Bearer token in localStorage, no login rate limit, no password reset. Next: httpOnly cookie, rate limiting, SSO.
  • The fake infrastructure keeps state in memory. Restarting it makes every server vanish; the reconciler then stops billing them (correct for the fake, noisy in a demo).
  • Search uses ILIKE. Fine for this size; next: trigram indexes or keyset paging.
  • Docker Compose was written but could not be run on my machine (Docker engine did not start); the same commands were run natively against PostgreSQL.

"You charged us for an IP we removed yesterday." Are they right?

  1. Open IP pool → the address (/ips/:id). "Who held it" shows every assignment with its period; the removal is the until of their last row. audit_log (ip.release, ip.move or server.terminate) says who did it and when.
  2. The same page lists every hourly charge of that IP with the payer and the server that held it.
  3. Rule: the hour in which it was removed is charged (a started hour counts), later hours must belong to someone else or no one.
  4. If a charge to them starts after that hour, they are right: refund it from the customer page (once, exact amount, enforced) and treat it as a bug.
-- charges to the customer after the hour they let go of the IP
select l.id, l.hour_start, l.amount
from ledger_entries l
where l.ip_id = $ip and l.customer_id = $customer
  and l.kind = 'charge'
  and l.hour_start >= date_trunc('hour',
      (select max(upper(during)) from ip_assignments
       where ip_id = $ip and customer_id = $customer), 'UTC')
      + interval '1 hour'
  and not exists (select 1 from ip_assignments a
       join server_usage u on u.server_id = a.server_id
       where a.ip_id = l.ip_id and a.customer_id = l.customer_id
         and a.during * u.during &&
             tstzrange(l.hour_start, l.hour_start + interval '1 hour'));

Empty result: the charges are correct, and the IP page shows them why.
